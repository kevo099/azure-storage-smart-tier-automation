## Writer-definition propagation recovery

At 05:33:15 UTC the pinned helper successfully created the fixture-scoped writer definition. Its immediate
scoped list did not return that definition, so it exited with `Created role is not readable yet` before
creating an assignment. The initial helper invocation therefore failed.

Recovery first read the created definition and verified all of the following:

- The fixed role name, full permission arrays and description matched the pinned
  [writer template](../infra/rbac/storage-remediator-role.template.json).
- Its only assignable scope was the owned fixture group.
- `createdBy` and `updatedBy` matched the known deployment operator.
- `createdOn` and `updatedOn` fell inside the recorded helper invocation's time window.
- No assignment used that role; the Automation identity still had only the intended reader.

The recovered immutable GUID then passed three successive exact-ID GETs, ten seconds apart, using API
`2022-04-01`. Only the helper's existing-definition `az role assignment create` command was retried with
that saved ID. No role-definition creation was repeated. The assignment completed at 05:36:09; the named
writes began afterward. See Microsoft's [Role Definitions — Get](https://learn.microsoft.com/rest/api/authorization/role-definitions/get?view=rest-authorization-2022-04-01)
for the exact-ID read contract and returned ownership fields.

The walkthrough now records the operator object ID, helper invocation window, complete output and exit
code, then provides the saved-ID recovery commands. This is an explicit adaptation to the initial helper
failure, rather than a claim that the unchanged initial grant invocation passed.
