## Why the original pin passed offline but failed in Azure

`git rev-parse v1.1.0` returned an annotated tag object's ID. Git commands such as `git show REF:path` and
ancestry checks peeled that object automatically, so the file and history looked correct locally. The
GitHub raw-content URL containing that object ID returned 404. `git rev-parse 'v1.1.0^{commit}'` produced
the usable commit ID; its raw URL returned the same qualified bytes with HTTP 200.

Azure's runbook API consumes a content URL through `publishContentLink.uri`; it cannot use an unavailable
raw URL. Microsoft documents that contract in [Runbook — Create Or Update](https://learn.microsoft.com/rest/api/automation/runbook/create-or-update?view=rest-automation-2024-10-23).
Azure's PSRule guidance also calls for a specific commit in the URL. See
[Azure.Automation.RunbookPinned](https://azure.github.io/PSRule.Rules.Azure/en/rules/Azure.Automation.RunbookPinned/).
The tag-versus-commit finding itself is supported by the recorded Git object types and live HTTP results.

A separate private test-driver assertion initially expected the runtime package key `Az`; the service
returned `az`. The driver was corrected to compare that key without case sensitivity while still requiring
version `12.3.0`. This was a test-driver issue; the guide's runtime instructions and deployment were correct.
